# CYBER//DIVE — แบบเกมสำหรับตรวจอนุมัติ

สถานะ: ฉบับเสนอ วันที่ 15 พฤศจิกายน 2026 ยังไม่ได้เริ่มสร้างเกม

## เป้าหมายที่ตกลงแล้ว

สร้างเกมใหม่แยกจาก CatchLab ซึ่งส่งงานเสร็จแล้ว เกมยิงยานแบบ on-rails 2.5D บน Windows ใช้ Unity URP ภาพดำ–ขาวแบบ point cloud/dither/ASCII ผสม HUD แบบ terminal ตามคลิปอ้างอิงและภาพคอนเซปต์ที่สร้างในแชต สีฟ้าเน้นโล่และการสะท้อนกระสุน

ESP32-S3 รับ FSR/Joystick เพื่อควบคุมซ้าย–ขวา Raspberry Pi 4 RAM 4 GB + Camera Module 3 ตรวจท่าทางและส่ง MQTT ผ่าน Wi-Fi เดียวกัน กล้องเพิ่มสกิลพิเศษ ผู้เล่นยังเล่นพื้นฐานได้เมื่อกล้องหลุด คอมเป็นเครื่องรันเกมและ Bridge; Pi ไม่เรนเดอร์เกม

## แนวทางที่พิจารณา

1. CYBER//DIVE: บินตามเส้นทาง หลบและสะท้อนกระสุนตามจังหวะเพลง ขอบเขตชัดและใช้ฮาร์ดแวร์ได้เด่น ผู้ใช้เลือกแนวนี้
2. NEURAL SWARM: เอาตัวรอดในสนามและเลือกอัปเกรด เล่นซ้ำได้มาก แต่ระบบศัตรู/อัปเกรดและการบาลานซ์ใหญ่กว่า
3. ZERO SIGNAL: บินหลบระบบรักษาความปลอดภัยด้วยท่าทาง แปลกใหม่แต่พึ่งการตรวจจับกล้องมากกว่า

เลือกรูปแบบ 2.5D แทนการบิน 3D อิสระ: โมเดลและฉากมีความลึกจริง แต่ล็อกตำแหน่งการเล่นเป็นแนวซ้าย–ขวาเพื่อใช้ FSR ได้

## ข้อเสนอรายละเอียดจากผู้ช่วย

รายละเอียดในส่วนนี้เป็นค่าเริ่มต้นที่ผู้ช่วยเสนอ ยังไม่ใช่รายละเอียดที่ผู้ใช้เคยยืนยันทั้งหมด

### วงจรการเล่น

- หนึ่งภารกิจประมาณ 2 นาที: สอนเล่นสั้น ๆ → ฝ่าฝูงโดรน/กำแพงข้อมูล → บอส WARDEN CORE → หน้าผล
- ยานอยู่ช่วงล่างของจอ ฉากและภัยเคลื่อนตามแกนลึกเข้าหายาน การเอียงยานเป็นภาพประกอบการเคลื่อน ไม่ใช่การบิน 6 แกน
- ยิงด้านหน้าอัตโนมัติ ผู้เล่นจัดตำแหน่งให้ตรงเป้าหมายและหลบกระสุนที่ Parry ไม่ได้
- กระสุนที่สะท้อนได้มีสัญลักษณ์และวงเตือนก่อนถึงตัว ต่างจากสิ่งกีดขวางด้วยรูปทรงด้วย ไม่ใช้สีอย่างเดียว
- กดสกิลหรือทำท่าจะเปิดโล่ประมาณ 0.6 วินาที คูลดาวน์เริ่มต้น 2 วินาที สะท้อนสำเร็จเพิ่ม SYNC และตัวคูณคะแนน เป้าหมายเน้นความรู้สึกสนุกมากกว่าการจับจังหวะระดับมิลลิวินาที
- SYNC เต็มเปิด Overdrive อัตโนมัติช่วงสั้น เพิ่มอำนาจยิงและเอฟเฟกต์; ยังไม่มีท่าที่สองในรุ่นแรก
- HULL 3 หน่วย เมื่อชนเสีย 1 และมีช่วงอมตะสั้น ๆ; HULL เป็นศูนย์จบด้วย SYSTEM FAILURE กำจัดบอสจบด้วย BREACH COMPLETE หากหมดเวลาภารกิจแล้วยังไม่ชนะถือว่าภารกิจล้มเหลวและมีปุ่มลองใหม่
- คะแนนมาจากทำลายศัตรูและสะท้อนกระสุน คูณด้วย SYNC สูงสุด x8 ถูกชนรีเซ็ตตัวคูณ หน้าจบแสดงคะแนน Parry สำเร็จ จำนวนครั้งที่ชน และเวลารอด

### การควบคุมและกล้อง

- ESP32 ใช้ FSR สองตัวหรือจอยแบบเลือกทีละโหมด ตามพฤติกรรมเดิม กดพร้อมกันหยุด; ข้อมูลเก่าหรือหลุดให้การเคลื่อนกลับศูนย์
- Pi รุ่นแรกตรวจเพียงการยกแขนข้างที่ว่างให้ข้อมือสูงกว่าไหล่ เพื่อให้มืออีกข้างยังจับจอยได้ เลือกซ้าย/ขวาได้จาก config; ทดลองท่าจริงและความมั่นใจร่วมกับเพื่อนก่อนล็อก threshold
- ทำท่าค้างไม่ยิงซ้ำ ต้องลดแขนกลับท่าปกติก่อนจึงเตรียมยิงครั้งใหม่ ไม่สะสมคำสั่งไว้ยิงภายหลังคูลดาวน์
- กล้องหลุดหยุดรับสกิลจากกล้อง แสดง DISCONNECTED และใช้ Space ทดแทนได้ การกลับมาเชื่อมต้องผ่านท่าปกติก่อนเปิดสกิลใหม่
- ใช้ A/D และ Space จำลองอุปกรณ์ได้ตั้งแต่วันแรก รุ่นแรกไม่รอเพื่อนทำ pose detection เสร็จ
- เพลงใช้ไฟล์เสียงที่มีสิทธิ์ใช้ กำหนด BPM และ timeline การโจมตีไว้ล่วงหน้า ใช้ Unity DSP clock ไม่วิเคราะห์เพลงแบบสด
- กล้องมีความหน่วง จึงต้องมีช่วงเตือนท่าก่อนโจมตีและค่าชดเชยปรับได้ วัดความหน่วงจริงก่อนเรียกการจับจังหวะว่าแม่นยำ

### งานภาพ

- เริ่ม Unity 3D URP ใหม่ในโฟลเดอร์ CyberDive รุ่น Editor 6000.5.2f1 เป้าหมาย Windows x64
- โมเดลยาน/บอสใช้ทรงเรขาคณิตอ่านง่าย ภาพ point cloud/dither ผ่าน shader และวัสดุเฉพาะ ไม่ต้องใช้ข้อความ ASCII ปกคลุมทั้งจอตั้งแต่แรก
- แยก HUD คมชัดจาก post-process ของฉาก สไตล์ต้องไม่กลบช่องหลบกระสุน
- Cinemachine ใช้กล้อง/แรงกระแทก, ProBuilder สร้างฉากทดลอง, VFX Graph ทำอนุภาคเสริม ระบบชนและกระสุนสำคัญทำด้วย gameplay objects/pooling ไม่ผูกกับ VFX particles
- ติดตั้งแพ็กเกจเข้ากับโปรเจกต์ใหม่ผ่าน Package Manager; ของที่ผู้ใช้ติดตั้งอยู่ใน CatchLabFriend ไม่ได้ติดตั้งให้ทุกโปรเจกต์อัตโนมัติ ไม่เปลี่ยนไฟล์เกมเก่า
- เป้าหมาย 1080p 60 fps บนคอมผู้ใช้ ต้องวัด GPU จริงก่อนยืนยัน ทำระดับคุณภาพให้ลดจำนวนอนุภาค ความละเอียดเอฟเฟกต์และ screen shake ได้
- มีตัวเลือกปิด flash/glitch/กล้องสั่น

### การเชื่อมอุปกรณ์

- ใช้ Bridge สำหรับเกมใหม่นอก ControllerBridge เดิม เช่น CyberDiveBridge โดยนำพฤติกรรมที่จำเป็นมาใช้ แยกโปรแกรมและคู่มือชัดเจน ห้ามรัน broker สองตัวบน IP/พอร์ตเดียวกัน
- คง topic ESP32 `catchlab/controller` และรูปแบบ CSV เดิมเพื่อใช้ firmware เดิม; topic กล้อง `catchlab/pose`; Pi client ID ต่างจาก ESP32
- broker อยู่คอม รับ Wi-Fi LAN TCP 1883 มี authentication ใช้ไฟล์ตั้งค่าส่วนตัวนอกเอกสาร ส่วนเกมเรียก HTTP loopback 127.0.0.1:8787
- `/controller/latest` สำหรับการเคลื่อน `/pose/latest` สำหรับสถานะกล้อง และข้อมูล session/revision จาก Bridge ป้องกันคำสั่งซ้ำ
- เสนอ pose JSON v1: `{"v":1,"sessionId":"pi-boot-unique","seq":42,"gesture":"PARRY","active":true,"confidence":0.91}` ส่งสถานะประมาณ 10 Hz พร้อม NONE เมื่อลดแขนหรือไม่พบท่า, qos=0, retain=false
- sessionId เปลี่ยนทุกครั้งที่เปิดโปรแกรม seq เพิ่มใน session เวลาอายุใช้เวลารับของ Bridge ไม่พึ่งนาฬิกา Pi และคอมตรงกัน
- Bridge ตรวจ JSON, enum, ขนาดและค่าตัวเลข; ข้อมูลเกิน 500 ms ถือว่า stale ส่งสถานะ invalid; ESP32 ใช้ timeout เดิมประมาณ 200–350 ms
- Unity เริ่มต้น/กลับเข้าเกมด้วยสถานะ unarmed รอ NONE สดก่อนจึงรับขอบสัญญาณ active ใหม่ หลัง pause กลับมาต้อง re-arm; เมนู/ช่วงตายไม่ใช้สกิล
- สัญญา API เต็มและวิธี reconnect ให้กำหนดในแผน โดยต้องทดสอบส่งซ้ำ ข้อมูลค้าง กล้องหาย และ Pi restart; HUD แสดงข้อมูลกล้องเชื่อมต่อจริง แยกจากคุณภาพการเห็นคน
- เพื่อนรับผิดชอบกล้อง จำแนกท่าและ MQTT ฝั่ง Pi ฝั่งเรารับผิดชอบเกม Bridge เครื่องมือจำลองและเอกสารสัญญา ไม่ส่งวิดีโอตลอดเวลาหรือบันทึกภาพผู้เล่นเป็นค่าเริ่มต้น

## ขอบเขตต้นแบบแรกที่ควรสร้าง

สร้าง vertical slice ที่เล่นได้ประมาณ 30–45 วินาทีก่อน: ยานหลบซ้ายขวา ยิงอัตโนมัติ ศัตรูหนึ่งแบบ บอสต้นแบบหนึ่งตัว สกิล Parry หนึ่งท่า HULL/SYNC/คะแนนและลองใหม่ พร้อม shader ทดลองและ HUD ใช้คีย์บอร์ดและตัวจำลอง MQTT ได้ จากนั้นทดสอบอุปกรณ์จริง ก่อนขยายเป็นภารกิจ 2 นาทีและปรับภาพให้ใกล้คอนเซปต์

เกณฑ์ผ่าน: คีย์บอร์ดเล่นจบและแพ้ได้; ESP32 ขยับได้ระหว่าง Pi เปิดสกิล; ทำท่าค้างไม่ใช้สกิลซ้ำ; กล้องหลุดไม่เกิดสกิลค้าง; reconnect ไม่ยิงเอง; ภาพศัตรู/ทางหลบอ่านได้ และวัด frame time บนเครื่องจริง

## ไม่ทำในรุ่นแรก

Multiplayer, open world, บิน 3D อิสระ, ระบบอัปเกรดหลายร้อยชิ้น, เพลงวิเคราะห์สด, ท่าทางหลายคน และ cloud leaderboard ไม่อยู่ในรุ่นแรก คะแนนเก็บในเครื่องได้ ยังไม่ย้าย schema Firebase/Sheets จากเกมเก่าที่มี validation เฉพาะรับของ

## สิ่งที่ให้ผู้สร้างตัดสินใจ

โครงสร้าง C# และชื่อ classes, รูปทรงโมเดลต้นแบบ, สูตร trajectory, pooling, เวอร์ชันแพ็กเกจที่เข้ากันได้, ตัวเลขบาลานซ์ระหว่างทดลอง, shader implementation และวิธีส่ง revision ของ HTTP โดยรักษาข้อกำหนดเรื่องอายุข้อมูล/ไม่เปิดสกิลซ้ำด้านบน

## ขั้นถัดไป

ตรวจแบบนี้กับผู้ใช้ก่อนสร้างโปรเจกต์หรือโค้ดเกม หลังอนุมัติจึงเขียนแผน implementation พร้อมลำดับการทดสอบ และเริ่มต้นแบบ
